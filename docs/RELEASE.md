# Munch — Release Guide (TestFlight / App Store)

How to take Munch from the current code-complete state to a signed build on
TestFlight. This is the **Phase 6** hand-off doc: it lists exactly what the
engineering work already covers, and the **user-only** steps (paid Apple/Firebase
consoles) that no code change can do for you.

Cross-references: `docs/APP_STORE.md` (App Privacy answers, review notes, §7
readiness checklist), `docs/RUNBOOK.md` (deploy + secrets + seed), `docs/
DECISIONS.md` (D-001 Windows/CI, D-003 cost floor, D-013 Apple revoke, D-019
Firebase).

---

## 0. What is already done (no further code needed)

- **Sign in with Apple — client flow:** `SignInView` → `AppleNonce` (nonce +
  SHA-256) → `FirebaseAuthProvider.completeSignIn` → `APIClient.linkApple`. All
  FirebaseAuth calls are behind `#if canImport(FirebaseAuth)`; with the SDK
  absent the app falls back to `DemoAuthProvider`.
- **Sign in with Apple — server:** `POST /v1/auth/apple-link` exchanges the Apple
  authorization code for a refresh token and stores it per uid.
- **Account deletion (D-013 / TN3194):** `DELETE /v1/account` purges events →
  **revokes the stored Apple refresh token at Apple** → drops it → deletes the
  profile + Firebase user. Unit-tested with a fake Apple client.
- **App icon:** a TestFlight-valid 1024² `AppIcon` ships in
  `ios/Munch/Munch/Resources/Assets.xcassets`, generated by
  `tools/make_app_icon.py`. (Final art is the Phase 8 design deliverable.)
- **Entitlement:** `com.apple.developer.applesignin` is declared in
  `project.yml` + `Munch.entitlements`, so it ships from the first archive.
- **Versioning:** `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` flow from
  `project.yml` into the Info.plist (the `CFBundleShortVersionString` /
  `CFBundleVersion` mapping is already wired — bump them in `project.yml`).
- **Privacy:** `PrivacyInfo.xcprivacy` audited and consistent (`APP_STORE.md` §2).

## 1. User-only prerequisites (paid consoles — blocking)

None of these can be done from the repo; they need the enrolled Apple Developer
account and the Firebase console.

### 1a. Apple Developer (developer.apple.com → Certificates, IDs & Profiles)
1. **App ID:** register the bundle id **`com.munch.app`** (must match
   `PRODUCT_BUNDLE_IDENTIFIER` in `project.yml`). Enable the **Sign in with
   Apple** capability on it.
2. **Services ID:** create a Services ID for Sign in with Apple (e.g.
   `com.munch.app.service`). This becomes `APPLE_SERVICE_ID` (the `sub`/`client_id`
   of the client secret).
3. **Sign in with Apple key (.p8):** Keys → create a new key with *Sign in with
   Apple* enabled. **Download the `.p8` once** (Apple never shows it again). Note
   the **Key ID** (`APPLE_KEY_ID`) and your **Team ID** (`APPLE_TEAM_ID`).
   - The `.p8` is a **file secret** — never commit it; never paste it into
     `.env.example`. It goes into Secret Manager / Cloud Run only (§4).

### 1b. App Store Connect (appstoreconnect.apple.com)
1. Create the **Munch** app record (same bundle id).
2. **Business → trader status:** complete the DSA trader-status declaration —
   required even for US-only distribution or the app cannot be submitted
   (`APP_STORE.md` §5).
3. Generate an **App Store Connect API key** (for the fastlane upload in §3).

### 1c. Firebase console (project **food-5eb2a**, D-019)
1. **Authentication → Sign-in method → Apple:** enable the Apple provider; fill
   in the Services ID, Apple Team ID, Key ID, and the `.p8`. (This is what lets
   Firebase mint ID tokens from the Apple credential.)
2. **Project settings → your iOS app:** register the iOS app with bundle id
   `com.munch.app` and **download `GoogleService-Info.plist`**.

## 2. Link Firebase into the iOS build (user, one-time)

The default build is deliberately Firebase-free (cheap CI, $0 demo). Linking is
two edits the user makes on a Mac (or commits):

1. **Drop the config in:** place the downloaded `GoogleService-Info.plist` into
   `ios/Munch/Munch/Resources/`. It is **gitignored** on purpose — present it
   only in the release build.
2. **Add the FirebaseAuth SPM product** to `ios/Munch/project.yml`:

   ```yaml
   packages:
     MunchKit:
       path: Packages/MunchKit
     Firebase:
       url: https://github.com/firebase/firebase-ios-sdk
       from: "11.0.0"   # pin a version that ships PrivacyInfo.xcprivacy (APP_STORE.md §3)

   targets:
     Munch:
       dependencies:
         - package: MunchKit
         - package: Firebase
           product: FirebaseAuth
         - package: Firebase
           product: FirebaseCore   # FirebaseBootstrap gates on canImport(FirebaseCore)
   ```

   Link **both** products: `FirebaseAuthProvider` gates on
   `canImport(FirebaseAuth)` and `FirebaseBootstrap` gates on
   `canImport(FirebaseCore)`. `FirebaseAuth` pulls in `FirebaseCore` transitively,
   but listing `FirebaseCore` explicitly keeps the bootstrap's import from
   silently breaking if that transitive edge ever changes. Once linked,
   `#if canImport(FirebaseAuth)` flips on and `FirebaseAuthProvider` does real
   sign-in. `FirebaseBootstrap.configureIfAvailable()` only activates when
   **both** the SDK is linked **and** the plist is bundled — so a misconfigured
   build degrades to demo auth rather than crashing.
3. **Re-audit privacy:** fold FirebaseAuth's bundled privacy manifest into
   `APP_STORE.md` §1–§3 (the three-places rule).

> Keep the no-Firebase default for the cheap `ios-build` CI lane. Only the
> archive/release path needs the plist + SPM product.

## 3. Signing + archive + upload (the release lane)

The repo is Windows-authored; archiving runs on **`macos-26`** in CI, no human
Mac required (D-001). The existing `ios-build.yml` builds **unsigned for the
simulator** — the release archive is a separate, signed lane to add.

1. **Signing config** in `project.yml` (replace the `FUTURE(Phase 6)` stub under
   `settings.base`):
   ```yaml
   DEVELOPMENT_TEAM: <APPLE_TEAM_ID>
   CODE_SIGN_STYLE: Manual
   CODE_SIGN_IDENTITY: "Apple Distribution"
   PROVISIONING_PROFILE_SPECIFIER: <App Store provisioning profile name>
   ```
2. **Bump the version** in `project.yml` (`MARKETING_VERSION`, and
   `CURRENT_PROJECT_VERSION` for each TestFlight build — it must increase per
   upload).
3. **Archive + export** (CI step, signed):
   ```bash
   cd ios/Munch && xcodegen generate
   xcodebuild -project Munch.xcodeproj -scheme Munch \
     -destination 'generic/platform=iOS' \
     -archivePath build/Munch.xcarchive archive
   xcodebuild -exportArchive -archivePath build/Munch.xcarchive \
     -exportPath build/export -exportOptionsPlist ExportOptions.plist
   ```
   `exportArchive` **requires** `ExportOptions.plist` — it does not exist in the
   repo (it carries account-specific ids; keep it out of git). Minimal template
   for an App Store / manual-signing export (fill in `<...>`):
   ```xml
   <?xml version="1.0" encoding="UTF-8"?>
   <!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
     "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
   <plist version="1.0">
   <dict>
     <key>method</key>            <string>app-store</string>
     <key>teamID</key>            <string><APPLE_TEAM_ID></string>
     <key>signingStyle</key>      <string>manual</string>
     <key>provisioningProfiles</key>
     <dict>
       <key>com.munch.app</key>   <string><provisioning profile name></string>
     </dict>
     <key>uploadSymbols</key>     <true/>
   </dict>
   </plist>
   ```
4. **Upload to TestFlight** via fastlane `pilot` (or `xcrun altool`/notarytool)
   using the App Store Connect API key from §1b — store the key as GitHub Actions
   secrets, never in the repo.

Secrets this lane needs (GitHub Actions secrets): the distribution certificate +
provisioning profile (base64), and the App Store Connect API key id / issuer id /
.p8.

## 4. Server-side Apple secrets (for the live revoke)

The account-deletion revoke (`apple_auth.py`) is dormant until all four `APPLE_*`
vars are set on the **reco service** (Cloud Run). Set them from Secret Manager
(see `.env.example` + `RUNBOOK.md`):

| Var | Value |
| --- | --- |
| `APPLE_TEAM_ID` | Apple Team ID (§1a) |
| `APPLE_KEY_ID` | Key ID of the Sign in with Apple `.p8` (§1a) |
| `APPLE_SERVICE_ID` | the Services ID (§1a) |
| `APPLE_PRIVATE_KEY` *or* `APPLE_PRIVATE_KEY_PATH` | the `.p8` PEM contents (inline secret) **or** a file path |

With any missing, `build_from_env()` returns `None`: account deletion still
purges all data, it just skips the live `/auth/revoke` call. **Verify the live
round-trip once** after wiring (create a test account via Sign in with Apple,
delete it, confirm a `200` from Apple's revoke endpoint in the logs).

Rotation: issue a new `.p8` → update the Cloud Run secret → delete the old key in
the Apple console.

## 6. Post-upload smoke test (TestFlight build)

1. Install via TestFlight on a real device.
2. **Sign in with Apple** → lands in onboarding (not the dev-auth shortcut).
3. Complete onboarding → swipe deck loads real venues → match screen CTAs
   (Directions / Call / order) hand off correctly.
4. **Profile → Delete my account** → confirm the account is gone (re-sign-in
   starts fresh) and the Cloud Run logs show the Apple `/auth/revoke` `200`.
